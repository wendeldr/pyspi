# pyspi calculation audit

An audit of every calculation pyspi performs: what each statistic is documented to be, what the
canonical literature definition is, what the code (and the third-party library it delegates to)
actually computes, how closely they agree, and where the time goes. It records; it does not fix.
Package code, tests and goldens are untouched by this directory.

The regression goldens under `tests/regression/goldens/` are snapshots of current output. Nothing in
this audit treats them as a reference for correctness; the references here are independent
implementations, analytic cases and external packages.

Code version: records cite package lines as `HEAD a1f20c7`. The branch has since moved to `a42ebc1`, which changes only `pyspi/workflow/`; every other package file is identical in both commits, so those line numbers hold at both. During the audit only `pyspi/calculator.py` changed among cited package files (commit `a1f20c7`); citations made at the earlier trace commit `36ac45a` were moved to current lines, and `checks/citations.py` screens every citation for stale or mismatched lines.

## Unit

A unit is one calculation at the level pyspi specifies it: a statistics class together with the
estimator/method/hyperparameter choice that selects a distinct code path. Variants that relabel the
same computation (`squared`, `mean`/`max` over a cached array, band selection of a cached spectrum)
are listed under the parent unit's `identifiers_covered`. Infrastructure units (preprocessing,
estimators shared by several classes) have no identifiers.

## Correctness columns and scoring

`verdict`: matches | variant | related-quantity | wrong | degenerate | unverified.
`check_method`: analytic | independent-impl | external-pkg | same-lineage | literature-only | unverifiable.
A reference is independent only if it does not import the library pyspi delegates to for that unit;
same-lineage references (rule R5 below says when a transcription counts as one) cap the score at 6.

Score anchors (0–10):

| Score | Anchor |
|---|---|
| 10 | Matches the canonical definition within floating-point tolerance (≤ 1e-8 relative) on an analytic or independent reference, and matches the pyspi supplement description |
| 9 | Matches canonical up to a trivial documented convention (squared vs not, ddof, log base, sign of a symmetric quantity), or within statistical tolerance consistent with estimator variance, or matches a MATLAB/author reference for optimiser-based units |
| 8 | Published variant with a monotone relationship to canonical (constant factor such as T/(T−1), abs of a signed canonical quantity, 1/m vs 1/m² scaling) |
| 7 | Matches the pyspi-supplement variant but differs from canonical in a value-changing way (bivariate instead of multivariate normalisation, LWR instead of OLS, expectation over 5 tapers, fixed-kernel GP), or an optimiser-based unit passing optimality checks |
| 6 | Library formula deviates from both the supplement and canonical in an interpretable way (signed PLI/wPLI, group-delay significance machinery, sigonly threshold/origin) |
| 5 | Stochastic/optimiser unit checked only qualitatively (direction, null, objective decrease), or a non-standard quantity with no literature definition computed as the code states |
| 4 | Related but different quantity (DI with block-entropy rate, arithmetic mean of wrapped phases, CCM max-E selection) |
| 3 | An identifier hyperparameter is ignored or the label does not describe the computation (softdtw constraints, dDTF bivariate, mgcx lag handling) |
| 2 | Substantially non-standard formula whose sign can differ from canonical (all-pairs PSI) |
| 1 | Wrong estimator substituted (te_symbolic → Gaussian) |
| 0 | Degenerate: constant, all-NaN, or wrong axis indexed |

`unverified` rows carry no score and state why. Finite-sample bias is not incorrectness: convergence
runs are reported separately from formula agreement, and constant offsets that are conventions
(ddof, log base, (T−1)/T, kernel ≤ vs <, 1e-8 jitter) are recorded as conventions.

### Score columns: original, rubric reading, adjusted

Three score columns sit side by side so that every number can be traced:

- `score_0_10` is the **original** score, assigned by the check stage (Workflow 2) and the verdict
  challenge (Workflow 4b). It is kept unchanged as the record of what was assigned. `verdict` is the
  original verdict word, kept the same way.
- `score_rubric` applies the anchor table above **as written**. When every condition of an anchor holds,
  `score_rubric_basis` is `anchor`. When no anchor's conditions all hold, the unit takes the highest
  anchor whose bar it clears, `score_rubric_basis` is `nearest-anchor`, and `score_rubric_note` names the
  clause of the next anchor that fails. `score_rubric_note` also explains every row where `score_rubric`
  differs from `score_0_10`.
- `score_adjusted` starts from `score_rubric` and applies clarifications that the anchor table does not
  state (rules R1, R2, R3 and R5 below). Each applied rule is named in `score_adjustment_rules`, with its
  evidence in `score_adjustment_reason`; when both are blank, `score_adjusted` equals `score_rubric`.
  `verdict_adjusted` is the verdict word under the same rules. It differs from `verdict` only where R1
  changes which identifier the row describes.

A rubric reading is `nearest-anchor` whenever no anchor's conditions all hold (45 of the 159 rows; 114 are `anchor`), and
`score_rubric_note` names the clause that fails. The situations that occur, with the units in each:

- the computation reproduces the canonical definition but the supplement's operational description differs, so anchor 10's
  second clause fails (rule R4: gpfit DotProduct, johansen order-0, the plain precision units, cov LedoitWolf and
  ShrunkCovariance, te.gaussian_k-1, multitaper_csm). Keyword, label, citation and version conflicts are metadata and do not
  count;
- the supplement does not mention the unit, so the supplement clause is read against GitBook (R3) or fails (pdist canberra,
  chebyshev and cityblock; preproc.detrend; misc.ids, whose anchor-7 clause is met only through the GitBook page);
- a floating-point shortfall that is not a convention (pdist euclidean and cosine);
- a convention that anchor 10's canonical clause does not allow and no anchor-9 clause names: the lcss tie rule (`<=` against
  `<`, distance.lcss.constraint-None), the sign of an antisymmetric quantity (causal.igci; anchor 9 names the sign of a symmetric
  one), JIDT's seeded 1e-8 jitter (infotheory.est.ksg1, je, ce and si kozachenko), te.kernel's box layout, and xcorr
  max_sig-False's T/(T-1), which is not a documented convention, so the unit takes anchor 8;
- an anchor that holds only in part, so the unit takes the next anchor below whose bar it clears: a supplement variant matched
  with a different parameter or orientation (the three cce units' n = 5 against the supplement's 10, basic.cov.OAS, johansen
  order-1, misc.coint.aeg, spectral.icoh through the 'unsigned' keyword only), an optimiser clause that fails (misc.lmfit.ElasticNet,
  infotheory.phi Geo norm-0 and norm-1, basic.cov.GraphicalLasso), a search or value map that is not monotone
  (te.gaussian_auto, distance.pdist.braycurtis), and base.pair_handling, whose deviation no anchor names;
- an output between two anchors: wavelet.phase, wavelet.pli and wavelet.wspli, where anchor 0's constant clause holds only for
  the max identifiers;
- a unit no anchor is written for: preproc.two_array_api, an infrastructure unit, read at anchor 3 with the documented z-score
  contract as its label;
- distance.softdtw, whose `score_rubric` 3 is its constraint identifiers' anchor because the anchor table has no rule for which
  identifier a row describes; R1 gives that rule in `score_adjusted`.

`distance.hhg` has the same supplement mismatch but is `anchor` 9: its one value deviation, tie rounding on
tied data, sits under anchor 9's estimator-variance clause, so an anchor-9 clause names it.

`documentation_status` records how the supplement relates to the computation. Verdict words follow the
glossary below and never set a score. No score column states that a value has been proven: a score
records how closely pyspi's output matched the audit's references on the audit's data.

The rubric reading differs from the original score in seven rows:

- pdist cosine, chebyshev and cityblock, 10 → 9: the supplement does not describe pdist, and cosine also
  misses 1e-8 relative on near-identical rows. R2 and R3 restore 10 in `score_adjusted`.
- basic.prec EmpiricalCovariance, LedoitWolf and ShrunkCovariance, 7 → 9: the canonical precision is
  reproduced to floating point, and the supplement's "partial correlation" description is the R4 case.
- infotheory.tlmi.kraskov, 9 → 10: its 9 rested on the supplement's "undirected" keyword, a metadata
  conflict that holds no other unit back (tlmi.gaussian is 10 with the same conflict).

| Column | Values | Meaning |
|---|---|---|
| `verdict` | verdict word | Original verdict (provenance) |
| `score_0_10` | 0–10; blank when `unverified` | Original score (provenance) |
| `score_rubric` | 0–10; blank when `unverified` | The anchor table as written |
| `score_rubric_basis` | `anchor` \| `nearest-anchor` \| `none` | `anchor`: every condition of that anchor holds. `nearest-anchor`: no anchor's conditions all hold; the highest anchor whose bar is cleared. `none`: unverified |
| `score_rubric_note` | text; required for `nearest-anchor` and whenever `score_rubric` ≠ `score_0_10` | Which clause of the next anchor up fails, or why the rubric reading differs from the original, with the deciding number or run |
| `documentation_status` | `described` \| `metadata-conflict` \| `misdescribed` \| `silent` | `described`: the supplement's operational description matches the computation. `metadata-conflict`: only keywords, labels, citations, typos, versions or prose order disagree. `misdescribed`: a reader implementing from the supplement text would get a different number. `silent`: the supplement does not mention the unit (GitBook used, R3) |
| `verdict_adjusted` | verdict word | `verdict` under rule R1 |
| `score_adjusted` | 0–10; blank when `unverified` | `score_rubric` after the rules named in the next column |
| `score_adjustment_rules` | blank, or IDs from {R1, R2, R3, R5} joined by `;` | Only rules that changed the number |
| `score_adjustment_reason` | blank, or `R2: <sentence>; R3: <sentence>` | One sentence per applied rule naming the run or number that triggers it |
| `identifier_exceptions` | blank, or `identifier=score (verdict): reason` joined by ` \| ` | Identifiers of the unit whose own anchor differs from the row's |

`validate_records.py` enforces these invariants:

- `score_adjusted` differs from `score_rubric` exactly when `score_adjustment_rules` is non-blank, and
  each applied rule has a reason;
- `nearest-anchor`, and any `score_rubric` that differs from `score_0_10`, has a note;
- `none` goes with a blank score;
- the verdict word fits the score, for both (`verdict`, `score_rubric`) and (`verdict_adjusted`,
  `score_adjusted`): `matches` 9–10, `variant` 5–8, `related-quantity` 2–5, `wrong` 1–3, `degenerate` 0.

The original pair (`verdict`, `score_0_10`) is not range-checked. The three precision rows carry
`matches` at 7 there.

Rules applied through `score_adjusted`:

- **R1, representative identifier.** A row's `score_adjusted` and `verdict_adjusted` describe the unit's base
  identifier. That is the `representative`, or, when the representative is a relabel of another
  identifier in the unit (`-sq`), that other identifier. Relabels carry the base score. Any other
  identifier in the unit whose own anchor differs is listed in `identifier_exceptions` with its anchor
  and reason (this is what moves `distance.softdtw` from 3 to 9: its two constraint identifiers are
  listed at 3). `build_units.py` therefore never makes a `-sq` identifier the representative.
  The fresh timings of `basic.kendalltau` and `basic.spearmanr` were taken on their `-sq` identifiers
  before this change; the square adds one elementwise operation.
- **R2, absolute floor.** An entry agrees when |pyspi − ref| ≤ 1e-8·|ref| or |pyspi − ref| ≤ 1e-12. The
  floor covers entries that are zero up to rounding. `checks/compare.py` judges every `exact` run with
  rtol 1e-10 and atol 1e-12, so the comparisons were never run under a pure relative test, and their
  relative bar is tighter than the anchor's 1e-8.
- **R3, documentation source.** The documented definition is the supplement. Where the supplement does
  not mention the unit at all, the GitBook page is the documented definition, and anchor 10's "matches
  the pyspi supplement description" is read against it. Where the supplement mentions the unit, GitBook
  text never overrides it.
- **R5, transcriptions.** A reference is same-lineage, whether or not it imports the delegate, when the
  sequence of operations that produces its number was written out from the delegate's source code and
  no paper, textbook or supplement sentence defines that sequence. Agreement with such a reference would
  survive a bug in the delegate. Copying a free choice from the delegate's source into a reference whose
  algorithm comes from a paper, textbook or the supplement does not make it same-lineage; free choices
  include ddof, log base, units, jitter, default hyperparameters, taper count, band or mask rule, tie
  rule, stopping rule and start value. A score above 6 needs at least one of the following agreeing with
  pyspi on the quantity the anchor asserts (the canonical quantity for 8–10, the supplement's variant
  for 7):
  - a reference of the second kind;
  - an analytic case;
  - a package from another lineage.

  Every unit scored above 6 was examined, and none rests only on a transcription, so R5 changes no
  number. The units examined include the auto-embedding TE units, phi star norm-1, the box-kernel
  infotheory units, cce kernel, Wilson factorisation, OAS, Johansen order-1, pec, reci and DBA.

Reading rules that change no number relative to `score_rubric` (they explain it):

- **R4, code canonical, documentation different.** Suppose the computation reproduces the canonical
  definition, but the supplement's operational description differs: a different statistic, estimator,
  parameter value or lag semantics, such that a reader implementing from the supplement text would get a
  different number. Then anchor 10's second clause fails, and the unit takes 9 with
  `score_rubric_basis = nearest-anchor`. Keywords, class labels, citations, typos, version numbers and
  loose prose order are metadata conflicts. They are recorded in `deviation_from_documented` and
  `documentation_status` and do not block 10.
- **R6, verdict words.**
  - `matches`: the canonical quantity, exactly or up to a trivial convention.
  - `variant`: the canonical quantity with a value-changing but interpretable modification.
  - `related-quantity`: a coherent, definable quantity that differs from the canonical one (all-pairs
    PSI, the arithmetic mean of wrapped phases).
  - `wrong`: the computed formula is not the quantity the code or its delegate cites, and is not a
    coherent alternative definition (`spectral.dcoh`'s mixed powers). An identifier whose named
    hyperparameter is silently ignored, so that it duplicates another identifier, is `wrong` (anchor 3):
    the identifier names a quantity that is never computed (lcss and softdtw constraints).
  - `degenerate`: constant, all-NaN or wrong axis.

  The word describes the output, not the defect: the same window rule gives `related-quantity` for
  xcorr `max_sig-True` (the maximum still usually finds the cross-correlation peak) and `wrong` for
  `mean_sig-True`. `unverified` means no comparison was run. No verdict word means a value has been
  proven.
- **R7, wording.** Anchor 5 reads "checked only qualitatively".

Readings of the anchor table that reviewers raised but that were deliberately not applied to any score column are listed in
`_handoff/score_columns_open_readings.md`, with the record each concerns; its last section, `score_columns_followups`, names
the 20 records whose `what_changed` later gained a sentence ('Rubric reading is ...') pointing from the original reasoning for
`score_0_10` to the anchor clause that `score_rubric_note` says fails. The spec and the scripts that filled
the three score columns are `_handoff/score_columns_spec.md` and `_handoff/score_columns_scripts/`.

## Optimisation columns

Timings follow the protocol in `profiles/profile_units.py` (shapes 7×100, 8×256, 8×1024, 32×1024,
118×1024 when the projection fits a 120 s budget; fresh and family-warm modes; `measure_mode` says
whether a number was measured or extrapolated; units listed in `profiles/infeasible_above_8x1024.txt` were never run above 8×1024 and are projected to 118 channels by pair count alone, `extrapolated-pairs-from-8`, which assumes no fixed per-window cost; spectral.sgc.nonparametric, a multivariate class whose cost is the delegate's loop over unordered pairs, is projected by that pair count (`PAIR_LOOP_BASIS` in `profile_units.py`), and the three causal.ccm units have no projection, because their 8×256 call took about 100 s, over the budget, so they were never run at 8×1024). The optimisation columns are a short search for where the time goes and which avenues look promising; nothing was optimised and, apart from a few cheap micro-benchmarks, no candidate code was written. `expected_speedup` is an order of magnitude for the unit's per-window cost at 118×1024, bounded by Amdahl from the cProfile share the avenue removes; its lower bound is at or below the ratio its cited evidence gives against the ranking basis (rounded down, never up); `speedup_basis` is `profile:<pstats> <frame> <share>%` plus `complexity:<argument>`, or `microbench:<profiles/micro file>` where one exists. `output_risk` is bit-identical | within-tolerance | semantic | rng-stream, prefixed `unverified-` unless a micro-benchmark diff file backs it.

Ranking (`build_csv.py`: `priority_rank` 1..N over opportunity rows; the columns `rank_basis_s` and `rank_rule` say what each row
was ranked on, `basis_scope` and `basis_scope_note` which identifiers its basis covers, and `subsumed_by`, `independent_of`,
`residual_speedup`, `eeg_applicable` and `speedup_kind` are copied from the record; `records/SCHEMA.md` lists the record keys):

1. **Basis.** A unit's basis is `projected_patient_s = projected_window_s_118 × 600`, family-warm when present, else fresh, summed
   over the unit's configured identifiers. Rows in tier 0 rank on the EEG selection where the timings allow it; `basis_scope` says
   which identifiers the basis covers and `basis_scope_note` why:
   - `retained-identifiers` (41 of the 53 retained units): the configured identifiers are the retained ones (40 units), or the
     family-warm run at 118×1024 timed every retained identifier before the non-retained ones and the basis is the retained
     identifiers' increments × 600. That applies to basic.kendalltau, whose EEG selection keeps kendalltau-sq alone: 4.52 s per
     window, 2,711 s per patient instead of the configured 5,420 s.
   - `retained-identifiers-approx` (1 unit): the record sets `optimisation.eeg_basis: retained-increments`, and the basis is the
     retained identifiers' family-warm increments × 600 although some EEG identifiers were never timed and are left out. That is
     spectral.plv: its retained band was timed first in the unit and holds plv's one build (7.80 s per window, 4,681 s per patient).
     Its configured sum (15.92 s) also holds a first-insert duplicate build (8.04 s) that an EEG run pays on spectral.phase, the
     first spectral class in `pyspi/workflow/retained185.yaml`. Its 10 untimed EEG bands read the cached array and are left out, so
     this basis understates plv's EEG cost by those reads.
   - `configured-identifiers-approx` (11 units): the basis stays the configured sum. `basis_scope_note` gives the counted reason,
     followed by the record's `optimisation.basis_scope_note` where the direction is known. basic.cov.GraphicalLasso: the retained
     `cov-sq_GraphicalLasso` was timed after the non-retained `cov_GraphicalLasso` and reads its cache. The ten other retained
     spectral units: their EEG band variants (10 or 11 per unit) were never timed. In the units whose cache key is the measure alone,
     the untimed bands read the cached array, so the configured sum stands for one build plus band reads (spectral.phase's also
     holds the first-insert duplicate, which an EEG run pays there too). spectral.psi and spectral.gd key the cache by band, so each
     untimed band pays its own build and the configured sum understates their EEG cost.
   - `configured-identifiers`: rows outside tier 0, ranked on the configured identifiers.

   No timing is filled in for an untimed identifier. Cross-unit caches: a family-warm run times a whole family in one process, so
   a unit can read a cache that an identifier of another unit filled earlier in that run. `build_csv.py` (`_cross_unit_warm`) flags
   a tier-0 unit when, at the largest shape where both its walls were measured, its fresh wall exceeds 1.5× its family-warm wall and
   the family-warm run timed identifiers outside the EEG selection before it. An EEG run does not run those identifiers, so their
   fill may fall on this unit. The record's `optimisation.eeg_basis` decides each flagged unit, and its `basis_scope_note` says why:
   `fresh` ranks on the fresh projection, where the unit fills the cache in an EEG run (basic.prec.EllipticEnvelope: Covariance
   has no EllipticEnvelope in the EEG selection, 3.48 s per window, 2,085 s per patient instead of 0.11 s; basic.xcorr.max_sig-False:
   the first CrossCorrelation identifier of an EEG run fills the per-pair cache, 1.24 s per window, 743 s instead of 52 s).
   `family-warm` keeps the family-warm figure, where a retained identifier fills the same cache first in an EEG run
   (basic.prec.MinCovDet, basic.prec.GraphicalLasso and basic.prec.GraphicalLassoCV after the Covariance fits;
   basic.xcorr.mean_sig-False after xcorr_max_sig-False). These six units keep `retained-identifiers`, because their configured
   identifiers are their retained ones; a flagged unit whose record names no `eeg_basis` gets `configured-identifiers-approx`.

   A cross-cutting row (`profiles/crosscutting.yaml`) with an explicit `projected_patient_s` keeps it and takes `basis_scope`
   and `basis_scope_note` from the row (window-parallel, calc-vs-storage: configured-identifiers-approx). Otherwise the units its
   scope covers are grouped by the tier of rule 2 and each group becomes its own row, `unit_id` suffixed `/retained`,
   `/eeg-fc-family` or `/other` when the scope spans more than one tier, whose basis sums only that group's units, each on the
   basis its tier uses. On a cross-cutting row `identifiers_covered`, `n_identifiers` and `eeg_identifiers` list the identifiers of
   its units and `rank_units` lists the units (on a unit row `rank_units` is its own `unit_id`). Non-retained units' seconds
   never enter tier 0 through a cross-cutting row.
2. **Tier.** 0 = unit in the retained EEG selection; 1 = another unit of an EEG-FC family (`EEG_FC_FAMILIES` in `build_csv.py`);
   2 = the rest. A cross-cutting row with `eeg_relevant: false` puts every part in tier 2. An opportunity with
   `eeg_applicable: false` on a retained unit gives no gain on the EEG selection (`rank_corr-3` on basic.kendalltau, whose EEG
   selection keeps kendalltau-sq alone, so there is no second identifier to serve from a cache; `cov_prec_simple-2` on the four
   plain basic.cov units, because the Precision unit of the same estimator reads the cached fit, so skipping its pinvh in a
   cov-only run moves it to the prec identifier in an EEG run). Its row takes the tier the unit
   would have outside the selection and is ranked on the configured identifiers; the unit's tier-0 stacking leaves it out.
3. **Kinds: throughput last, projections last in their tier.** `speedup_kind` is `per-window` (default), `throughput` or
   `projection`. A `throughput` opportunity gets its figure from more cores (process pools over pairs or trials, BLAS threads,
   window workers) and saves no per-window CPU: `xc-window-parallel`, `xc-blas-threads`, `lmfit-5`, `gpfit-2`, `ccm-1`,
   `cov_prec_robust-2`, `cov_prec_glasso-1`. These rows rank after every per-window row, then by tier and the wall-clock seconds
   their figure removes. They compete for the same 32 physical cores, so their figures do not multiply: the ~8 memory-bounded
   window workers leave about 4 cores each for a pair pool. The pair pools are alternatives to `xc-window-parallel`, not built
   on it: their `expected_speedup` gives the figure alone and inside a window worker, and none lists `xc-window-parallel` in
   `depends_on`. A `projection` opportunity (`xc-gpu-spectral`, `xc-gpu-distance`) is a per-window saving projected for
   hardware or software that is not installed here, with no code run; it ranks after the other per-window rows of its tier.
   `it_kraskov-1` (opp_type parallel) stays per-window, because single-threading the JIDT calculator lowers the CPU seconds of
   each call.
4. **Overlap on one unit: stacking.** The savings of one unit's rows never add up past its basis. On each unit `build_csv.py`
   stacks the per-window avenues that apply to it (its own opportunities and the cross-cutting ones whose scope covers it). An
   avenue comes after every per-window avenue it names in `depends_on` (builds on) or `subsumed_by` (contained in), transitively;
   among the avenues free to go next, the one with the largest lower-bound speedup goes first (`projection` avenues after the
   others; ties by output risk, effort, id). `rank_basis_s` is the unit's basis divided by the lower-bound speedups of every
   avenue stacked before it, and `projected_patient_s_after = rank_basis_s / k`. `k` is the lower bound of `expected_speedup`,
   with two exceptions. `residual_speedup` replaces it on a unit where one of the avenue's `depends_on` prerequisites, or an
   avenue it is `independent_of` (disjoint frames, below), is stacked before it; the record gives the figure on that residual in `speedup_basis`, at or below what its evidence gives against the
   residual the ranking stacks on (the basis divided by the prerequisites' lower bounds). Mostly the prerequisite changes what the
   avenue acts on: spectral_csm-1 after spectral_csm-shared-csm on spectral.cohmag, spectral.icoh and spectral.psi is 1x, because the
   shared coherency is built once per Data, CoherencePhase runs first, and these units are later consumers with no coherency build
   left (spectral_csm-1's saving on the one build is credited on spectral.phase). On spectral.phase, the first consumer, three avenues
   stack: `spectral_coherence-1` (the first-insert key fix, 2x) first; then spectral_csm-shared-csm, which `depends_on` it and has
   `residual_speedup` 1x there, because phase keeps the one coherency build a first consumer pays and the duplicate the shared memo
   would also remove is already credited to `spectral_coherence-1`; then spectral_csm-1, whose `residual_speedup` is 1.6-2.6x by
   Amdahl from phase's coherency share (74.1% in its 118×1024 pstats) with the family-warm increments, its lower bound taken on the
   residual the ranking stacks on (the configured sum over spectral_coherence-1's 2x and shared-csm's 1x); its `expected_speedup`,
   1.7-2.7x, is the same model on today's two-build cost. spectral_phase_sync-1 after spectral_csm-1 is 1.36x on spectral.wpli and 1.46x on spectral.dswpli, because
   spectral_csm-1 halves the taper-level frames but not the rest of the call, so the repeated builds are a smaller share of its
   residual than of today's cost (on spectral.pli, spectral.dspli, spectral.ppc and spectral.plv the same link leaves the lower
   bound at 1x, the unit that pays the shared build); sgc-1 after sgc-3 on spectral.sgc.parametric_order-None is 1.3x, because the
   incremental search leaves only about 40% of the recursion that sgc-1 removes; it_kernel-1 and it_kozachenko-1 after it_kernel-2
   and it_kozachenko-2 have lower bound 1x because the per-channel terms' share of that residual is not known. The EEG order
   also sets some `expected_speedup` lower bounds directly. spectral_csm-shared-csm on spectral.cohmag,
   spectral.icoh, spectral.psi and spectral.gd has the later-consumer figure as its lower bound (cohmag 6x, icoh 2.7x, psi 6.7x by
   Amdahl on the build they no longer pay, against the configured sum, which on cohmag and icoh also holds 5 band reads that a later
   consumer still pays; gd 2x from un-profiled timings, 11.06 -> 5.25 s per window, because cProfile inflates gd's per-pair
   callbacks and so understates its coherency share), so the coherency build each of them drops is credited once, to that avenue; the first-consumer figure (about 1x on
   cohmag and icoh, 3.4x on psi) holds only in a run where the unit builds the coherency itself. cov_prec_simple-1 on
   basic.prec.EmpiricalCovariance, LedoitWolf, OAS and ShrunkCovariance has lower bound 1x for the same reason: Covariance runs
   before Precision, the prec unit reads the fit cached by its basic.cov sibling (its family-warm basis is that cache read), and
   the pinvh the avenue makes cheaper is paid, and credited, on the cov unit. A cross-cutting opportunity's `scope_speedup` entry
   gives the figure on the units its globs match (xc-gpu-distance: 1x on distance.hsic.*, which has no GPU projection of its own;
   xc-gpu-spectral: 1x on spectral.cohmag, spectral.icoh and spectral.psi, the later consumers above, so the one shared build is
   credited on spectral.phase alone; spectral.gd, also a later consumer, is outside that avenue's scope, because what its residual
   keeps is mostly per-pair Python callbacks that a GPU CSM does not move, `profiles/crosscutting.yaml`). Where a `subsumed_by` avenue applies (it is stacked on the
   unit in that plan; an avenue with `eeg_applicable: false` is not, so in tier 0 the avenue it subsumes keeps its own k, as
   `cov_prec_simple-1` does under `cov_prec_simple-2` on the plain basic.cov units), `projected_patient_s_after` equals `rank_basis_s`
   (no saving) and the avenue does not shrink later residuals. Cross-cutting
   rows apply this per covered unit and sum. `rank_rule` names the `depends_on` prerequisites, the subsumers and the unlinked
   avenues stacked before the row, each with `(on m of n units)` when it applies to only some of the row's units. Throughput
   avenues are not stacked and are never prerequisites: a `depends_on` entry that names one records a deployment precondition
   (`xc-window-parallel` and the cov/prec pools need the BLAS-at-1-thread part of `xc-blas-threads`) or pairing (per-window
   avenues meant to run inside window workers), not a ranking prerequisite. The record owner adds `depends_on` or
   `subsumed_by` when one applies, or `independent_of` when two avenues act on different parts of the unit's cost, so that the later
   one is not treated as building on the earlier (`rank_rule` then says "recorded as independent"). The parts are different
   factors (fewer calls times a cheaper call: the savings multiply, and the later avenue keeps its own k on the residual) or
   disjoint frames: the later avenue saves the same seconds as on today's cost, which are a larger share of the residual, so its
   record gives that figure as `residual_speedup` (spectral.gd: spectral_csm-shared-csm removes the Multitaper and coherency and
   spectral_psi_gd-1 the per-pair callbacks; shared-csm goes first with the larger lower bound, 2x, and spectral_psi_gd-1's 1.3x
   lower bound on today's 11.06 s per window, 2.55 s, taken off the 5.53 s residual is 1.86x, so its `residual_speedup` is
   1.8-4x; the ceiling on that residual is about 5x). Without any of them the stacking order alone decides which avenue is credited first
   and `rank_rule` says "no link".
5. **Order.** Per-window before throughput, then tier, then (within a tier) `projection` rows after the other per-window rows,
   then patient seconds saved (`rank_basis_s - projected_patient_s_after`, descending), then output risk (classes backed by a
   micro-benchmark diff before `unverified-` ones; bit-identical, within-tolerance, rng-stream, semantic), then effort (S, M,
   L, XL), then unit and opportunity id. `k` is the lower bound of `expected_speedup` (the first number before `x`), or of
   `residual_speedup` or `scope_speedup` where rule 4 says so. A row with no basis (blank `rank_basis_s` and
   `projected_patient_s_after`) counts as saving 0 s, so it comes after every row of its kind and tier with a positive saving and
   is then ordered by output risk and effort. That applies to the 22 opportunity rows of two kinds of unit: the infrastructure
   units, which have no identifiers and so no projection in `profiles/summary.json` (their cost sits inside the timings of the
   units that call them), and the units `summary.json` could not project to 118×1024 (the three causal.ccm units: 'no 118x1024
   measurement and no ok 8x1024 + 32x1024 records to fit'; their 8×1024 run was skipped over budget). Each such row's
   `speedup_basis` ends with the reason.

`profiles/micro/` file kinds. `opp_<opportunity_id>.py` / `.json` are the opportunity micro-benchmarks: the candidate code lives only
inside the script, and the JSON holds baseline and candidate timings and, for most of them, `max_abs_diff` / `max_rel_diff` /
`nan_mask_equal` against pyspi's output. Each Workflow 3 group wrote at most two (twelve in all). Only an `opp_` file can back a
`microbench:` basis, and only one with a diff can remove the `unverified-` prefix from an `output_risk`. `probe_*.py` / `.json` are
timing probes, not `opp_` micro-benchmarks: each times one premise of an avenue, runs no candidate code and compares no outputs, so
it is quoted inside a `profile:` / `complexity:` basis, does not count toward the two per group, and leaves `output_risk`
`unverified-`. Two come from the causal-misc group and one from infotheory.
`probe_ccm_threads` (CPU/wall of one pyEDM.CCM call at T=256) is cited by
ccm-1's `speedup_basis` in `causal.ccm.E-1`, `causal.ccm.E-10` and `causal.ccm.E-None`, and by `notes/ccm.md`. `probe_pec_combine`
(unprofiled wall share of mne_connectivity `combine('mean')` at 118×1024) is cited by pec-1's `speedup_basis` in the four `misc.pec.*`
records, by `hotspot_1` of `misc.pec.orth-False_log-False` and `misc.pec.orth-True_log-True`, and by `notes/pec.md`.
`probe_theiler_window_calls` (un-profiled wall of every `JIDTBase._set_theiler_window` call in the five Kraskov DCE units, fresh
processes) is cited by `hotspot_2` of `infotheory.mi.kraskov_DCE` and `infotheory.te.kraskov_DCE_auto-MAX_CORR_AIS_kmax-10_taumax-4`,
by `hotspot_1` and it_kraskov-3's `speedup_basis` in `infotheory.theiler_window`, and by `notes/it_kraskov.md`. `opp_it_kraskov-1.py`
has a `--only <shape>` mode that merges one shape into the existing JSON (`merged_runs` logs it); its `3x1024` cases are the
T=1024 measurement behind the it_kraskov-1 refutation comments in the two auto-embedding TE records. The other files
are profiles, not benchmarks: `prof_<group>.py` with its `.pstats` and `__index.json` (cProfile at 32×1024 or 118×1024),
`<unit>__<P>x<T>.pstats` / `__profile.json` (cProfile at shapes the profiling pass could not finish, or at 118×1024), and
`retime_wavelet.py` (isolated wavelet re-times, results in `prof_wavelet__index.json`). `_bench.py` is the shared timing helper.

Workflow 4c added merge modes to four `opp_` scripts; each writes into the existing JSON under its own key and logs the run in
`merged_runs` (argv, load average, note), leaving the earlier keys in place:

- `opp_spectral_csm-1.py --add ppc,wpli,dswpli [shapes]` times further measures with the sliced candidate in paired repeats
  (baseline then candidate on a fresh Data, 3 repeats) and stores them under `<identifier>__sliced` keys, with
  `<measure>_sliced_vs_golden` diffs against the 7x100 golden snapshot;
- `opp_spectral_csm-shared-csm.py --paired [shapes]` stores a same-run comparison under the top-level key `paired` (per shape:
  psi, gd and phase through pyspi, the key-fixed phase candidate, and one shared coherency read by phase, psi and gd, with the
  gd callback drivers timed without a profiler; the `merged_runs` note defines each ratio);
- `opp_cdt_pairwise-1.py --split118` and `opp_it_gaussian-1.py --split118` store `shapes['118x1024_split']`: Data construction,
  candidate math on one prebuilt Data and one fresh one-shot pyspi call, timed separately. The two define
  `candidate_incl_data_s` differently: in `opp_cdt_pairwise-1.json` it is its own timing (min of 5 of the candidate on a freshly
  built Data, 6.94 ms, not 3.10 + 3.19 ms), in `opp_it_gaussian-1.json` it is the sum of `candidate_math_s` and
  `data_construction_s`. Both notes in `merged_runs` say which.

Some speedup and premise figures come from throwaway runs that saved no output into these JSON files. The record or note then
names the scratch script by its scratchpad path (`scratchpad/<dir>/<script>`, packed by `checks/archive_probes.py`) and quotes
the figures, because the archive keeps scripts only.

## Blank cells in `metrics_audit.csv`

A blank cell means one of the following; nothing is filled in for a quantity that was not measured.

- **Cross-cutting rows** (`unit_id` `family:<name>`, `module` cross-cutting) carry no correctness data: every correctness and
  score column, the per-shape timings, `pyspi_class`, `hyperparameters`, `source`, `representative` and `pair_basis` are blank.
  Such a row describes an avenue across units, not a calculation; the correctness data are on the unit rows it lists in
  `rank_units`.
- **Infrastructure units** (13; `source` infrastructure, `pair_basis` n/a) have no identifiers, so `identifiers_covered`,
  `representative`, the timing columns, the projections and `rank_basis_s` are blank: `profile_units.py` times identifiers, and an
  infrastructure unit's cost sits inside the timings of its consumers. Their hotspots are read from consumer profiles.
  preproc.detrend, preproc.zscore and preproc.two_array_api have no profile frame at all, so `opaque_share` (and
  two_array_api's `hotspot_2`) reads `n/a: <reason>`.
- **`time_s_7x100_golden` and `machine_factor`** come from the per-SPI `time_s` of the regression goldens
  (`tests/regression/goldens/full/meta.json`), which cover the 285 `pyspi/config.yaml` identifiers only. They are blank for the
  13 infrastructure units, the 9 wavelet units whose identifiers come from `tests/regression/extra_config.yaml`, and
  basic.xcorr.max_sig-False, whose identifiers only the EEG selection names (23 units).
- **Timings above 8×1024 and projections.** `t_32x1024_s` is blank for the 37 units of `profiles/infeasible_above_8x1024.txt`
  (projected by pair count) and the infrastructure units; `t_118x1024_s` wherever the 118×1024 run was not made (the projection
  in `projected_window_s_118` and `measure_mode` say how the unit was projected instead). `projected_window_s_118`,
  `projected_patient_s` and `measure_mode` are blank where `summary.json` could not project the unit (the three causal.ccm
  units: 'no 118x1024 measurement and no ok 8x1024 + 32x1024 records to fit'); the family-warm projection is blank for those and
  for the three spectral.sgc parametric units, whose family-warm runs above 8×1024 were not made because the family includes
  spectral.sgc.nonparametric from the infeasible list (their fresh projections are measured at 118×1024). `P_exponent_measured` needs both 8×1024 and 32×1024. `t_per_pair_ms` is blank for units computed by one
  multivariate call per window (`pair_basis` multivariate), where no per-pair time is defined. `t_shared_family_s` is the
  family-warm increment of the timing family's first identifier (the call that fills any cache the family shares), written
  `<s> @<shape> (<identifier>)` at the largest shape with an ok family-warm record, and so the same on every unit of a family;
  `t_incremental_s` is the unit's own summed family-warm increments at the largest measured shape. Both are blank for the
  infrastructure units and the three causal.ccm units (no family-warm record at 8×1024 or above).
- **No opportunity** (22 units; every opportunity and ranking column blank, `priority_rank` too, except `opportunity`): the
  record's `optimisation.no_opportunity_reason` says why, and `build_csv.py` writes it into `opportunity` (each
  reason starts 'No opportunity' or 'No unit opportunity'). The six pdist units (one compiled call per
  window, about 24 ms per 118×1024 window for all six); base.pair_handling (its avenue is the cross-cutting
  `xc-undirected-upper`, row `family:undirected-upper/*`); preproc.two_array_api (not on the Calculator or EEG path); the three
  fixed-embedding Kraskov TE units (`it_kraskov-1` refuted for them, `opp_it_kraskov-1.json`); and the 11 wavelet units (the
  user's decision: the family is not used and its definition is under review).
- **Ranked rows without a basis**: see ranking rule 5 above.
- **Score adjustment columns**: blank `score_adjustment_rules`, `score_adjustment_reason` and `identifier_exceptions` mean no
  rule changed the number and no identifier differs ('Score columns' above). `eeg_identifiers` is blank for units outside the
  EEG selection.

## Regenerating

From the repository root, in the project venv unless noted:

```
.venv/bin/python audit/build_units.py                      # units.yaml from the live package
.venv/bin/python audit/briefing/build_briefings.py         # briefing packs
.venv/bin/python audit/checks/run_checks.py                # data -> pyspi outputs -> references -> compare (both venvs, R, Octave)
.venv/bin/python audit/checks/citations.py --only-problems # stale or mismatched file:line citations in records and notes
# timing pass B (quiet machine; 2-4 h): the 37 infeasible units stay at <= 8x1024
.venv/bin/python audit/profiles/profile_units.py --all --shapes 7x100,8x256,8x1024,32x1024 --modes fresh,family-warm \
    --budget-s 120 --force --infeasible $(grep -v '^#' audit/profiles/infeasible_above_8x1024.txt | paste -sd,) --out audit/profiles
.venv/bin/python audit/profiles/profile_units.py --shapes 118x1024 --units <units whose P=32 projection stays under 120 s> --out audit/profiles
.venv/bin/python audit/profiles/profile_units.py --all --shapes 8x1024 --profile --out audit/profiles   # cProfile pass
.venv/bin/python audit/profiles/profile_units.py --summarise --out audit/profiles                       # -> profiles/summary.json
.venv/bin/python audit/profiles/micro/opp_<opportunity_id>.py [shapes]   # one micro-benchmark (merge modes above)
.venv/bin/python audit/validate_records.py --stage profiled
.venv/bin/python audit/build_csv.py                        # both CSVs; --check fails if they are stale
.venv/bin/python audit/checks/archive_probes.py --scratch <scratchpad dir> [--dry-run]   # pack the cited scratch probes
```

The timing commands are the ones the audit ran (`HANDOFF.md`, Next steps 2 and 3); `--infeasible` takes comma-separated ids or
globs, not a path, and without it the 37 infeasible units would be tried at 32×1024 and 118×1024, which takes hours and does
not reproduce `summary.json`. CCM was re-timed at 7×100 and 8×256 with `PROFILE_WARMUP_SHAPE=7x100` (the default 8×1024 warm-up
took about 30 min per CCM identifier). Timings depend on the machine and its memory state, so a re-run gives similar, not equal,
walls.

`run_checks.py --family <family>` runs one family; `pyspi_outputs.py --force` recomputes runs whose
manifest entry changed. Reference npz contract (value, criterion, tolerances, reference_kind) is in the
`compare.py` docstring; `reference_kind` is what `check_method` in the record must not overstate.
`compare.py` marks every run whose pyspi side raised (index status not `ok`) as failed before it reads
the reference, so a reference cannot turn an expected exception into a pass. Where the expected outcome
is an exception, the family runs a project-venv probe that catches it and returns status codes, and the
reference judges those codes (e.g. `probes/spectral_coherence_bands.py:empty_max`,
`probes/xcorr_probes.py:sig_status`).

The comparison venv (no pyspi, no jpype) is built from `env/comparison-requirements.txt`; its path
is read from `$AUDIT_REF_PYTHON` or, when that is unset, `env/comparison-venv.path` (which still names the venv's original
`/tmp` location; the folder now lives in `~/Documents/pyspi-audit-scratch-2026-10-15/`, so set the variable, see `PATHS.md`). R references run through `Rscript`
with `R_LIBS_USER=~/R/audit-lib` (see `env/r-packages.txt`); Octave runs the archived PhiToolbox.
Reference material outside the repo: `/media/dan/Data/git/pyspiDocumentation/` (GitBook source and
`supplement/` with the paper's Supplementary Information PDF and its text extraction).
