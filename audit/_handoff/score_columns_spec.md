# Two-score-column spec (adopted 2026-10-15 from an independent adversarial review; the user said to follow it)

## Columns (records `correctness` block, placed directly after `score_0_10`)
| column | allowed values | meaning |
|---|---|---|
| score_0_10 | integer 0-10; null when verdict is unverified | The approved anchor table (audit/README.md) as written. |
| score_0_10_basis | anchor / nearest-anchor / none | anchor: every condition of the anchor at that score holds. nearest-anchor: no anchor's conditions all hold; the unit takes the highest anchor whose bar it clears. none: unverified. |
| score_0_10_note | text; required when basis is nearest-anchor, optional otherwise | Which clause of the next anchor up fails and why the row sits at this number (one or two sentences, with the number or run that decides it). |
| documentation_status | described / metadata-conflict / misdescribed / silent | described: the supplement's operational description matches the computation. metadata-conflict: only keywords, labels, citations, typos, versions or prose order disagree. misdescribed: a reader implementing from the supplement text would get a different number. silent: the supplement does not mention the unit (GitBook used under R3). |
| score_adjusted | integer 0-10; null when unverified | score_0_10 after the rules in score_adjustment_rules. Always filled when score_0_10 is. |
| score_adjustment_rules | empty string, or IDs from {R1, R2, R3, R5} joined by ";" | Only rules that changed the number. R4, R6, R7 never appear. |
| score_adjustment_reason | empty string, or "R2: <sentence>; R3: <sentence>" | One sentence per applied rule naming the run or number that triggers it. |
| identifier_exceptions | empty string, or entries "identifier=score (verdict): reason" joined by " | " | Identifiers of the unit whose own anchor differs from the row's. |

Invariants: score_adjusted == score_0_10 iff score_adjustment_rules is empty; rules non-empty => reason non-empty; basis nearest-anchor => note non-empty; basis none iff score null; verdict range (checked on score_adjusted, since R1 makes verdict and score_adjusted describe the base identifier): matches => >=9; variant => 5-8; related-quantity => 2-5; wrong => 1-3; degenerate => 0.

## Rules
R1 (score-changing, via score_adjusted): A row's score_adjusted and verdict describe the unit's base identifier: the representative, or, when the representative is a relabel of another identifier in the unit (-sq), that identifier. Relabels carry the base score. Any other identifier in the unit whose own anchor differs is listed in identifier_exceptions with its anchor and reason.
R2 (score-changing): An entry agrees when |pyspi - ref| <= 1e-8*|ref| or |pyspi - ref| <= 1e-12. The floor covers entries that are zero up to rounding. (compare.py exact runs actually use rtol 1e-10 AND atol 1e-12.)
R3 (score-changing): The documented definition is the supplement. Where the supplement does not mention the unit at all, the GitBook page is the documented definition and anchor 10's "matches the pyspi supplement description" is read against it. Where the supplement mentions the unit, GitBook text never overrides it.
R4 (README text only; never in score_adjustment_rules): When the computation reproduces the canonical definition but the supplement's operational description differs (a different statistic, estimator, parameter value or lag semantics, such that a reader implementing from the supplement text would get a different number), anchor 10's second clause fails and the unit takes 9 with score_0_10_basis = nearest-anchor. Keywords, class labels, citations, typos, version numbers and loose prose order are metadata conflicts; they are recorded in deviation_from_documented and documentation_status and do not block 10.
R5 (score-changing): A reference is same-lineage, whether or not it imports the delegate, when the sequence of operations that produces its number was written out from the delegate's source code and no paper, textbook or supplement sentence defines that sequence; agreement with such a reference would survive a bug in the delegate. Reading the delegate's source to copy a free choice (ddof, log base, units, jitter, default hyperparameters, taper count, band or mask rule, tie rule, stopping rule, start value) into a reference whose algorithm comes from a paper, textbook or the supplement does not make it same-lineage. A score above 6 needs at least one reference of the second kind, an analytic case, or an other-lineage package agreeing with pyspi on the quantity the anchor asserts (canonical for 8-10, the supplement's variant for 7). Applied to every row above 6 by the reviewer: changes none.
R6 (glossary only): wrong: the computed formula is not the quantity the code or its delegate cites and is not a coherent alternative definition. related-quantity: a coherent, definable quantity that differs from the canonical one. degenerate: constant, all-NaN or wrong axis. variant: the canonical quantity with a value-changing but interpretable modification. matches: the canonical quantity, exactly or up to a trivial convention. An identifier whose named hyperparameter is silently ignored so that it duplicates another identifier is wrong (anchor 3), not related-quantity, because the identifier names a quantity that is never computed (lcss and softdtw constraints). The word describes the output, not the defect: the same window rule gives related-quantity for xcorr max_sig-True and wrong for mean_sig-True. "unverified" means no comparison was run; no verdict word means a value has been proven.
R7: anchor 5 "verified only qualitatively" -> "checked only qualitatively"; rewrite other "verified" uses in records/notes to checked/compared/re-derived (keep "hash-verified" file-hash wording and schema words unverified/unverifiable).

## Basis guidance (F1)
Classify every 9 with verdict matches as `anchor` only if an anchor-9 clause literally names its deviation (ddof, squared vs not, log base, sign of a symmetric quantity, statistical tolerance consistent with estimator variance, MATLAB/author reference for optimiser-based units); otherwise `nearest-anchor` with a note. preproc.detrend and preproc.zscore need this look. In general: a row is `anchor` when its number's anchor text describes it; `nearest-anchor` when the record's own reasoning says no anchor fits exactly / "house mapping" / highest anchor cleared.
